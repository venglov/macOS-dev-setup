# Границы будущих платформ

Сегодня команды платформенного provisioning существуют только для macOS.
`bootstrap steamdeck`, `bootstrap proxmox` и похожие команды завершаются ошибкой.
Общие dotfiles не означают готовность ОС к разработке.

## Контракт расширения

Новый адаптер должен отдельно определить поддерживаемые OS/releases/CPU, роль
машины, доступный POSIX userland, writable user paths, способы установки и
обновления. Нужны предварительные проверки, минимальный профиль пакетов,
неинтерактивный PATH и проверка восстановления после прерывания/обновления ОС.
Только после этого можно подключать общие файлы через тот же source chezmoi.

Платформа предоставляет зависимости до `common apply`. Она не копирует общие
конфиги, не устанавливает автоматически весь terminal/desktop/dev-профиль,
не требует zsh/Homebrew/systemd/GNU utilities по умолчанию и не применяет dotfiles
к root. Повышение прав для конкретной операции ОС следует проектировать отдельно
от пользовательского bootstrap. Нельзя снять текущий root-guard ради удобства.

## Steam Deck / SteamOS

Сначала определить реальную установленную ОС и её версию: устройство может иметь
SteamOS, другую Linux-систему или изменённый образ. Проверить read-only root,
разделение `/home`, пользовательские контейнеры и доступные варианты приложений.

Valve предупреждает, что пакеты вне Flatpak, например pacman-установки, могут
исчезнуть при следующем обновлении SteamOS. Это не основание автоматически
отключать read-only защиту. Будущая проверка должна включать обновление ОС,
перезагрузку, сохранность dotfiles/runtime directories и повторный bootstrap.
[Официальный Desktop FAQ](https://help.steampowered.com/en/faqs/view/671A-4453-E8D2-323C).

Рассмотреть Flatpak для GUI и отдельное пользовательское/container dev-окружение,
проверив доступ к файлам, hardware и сетям. Проверить glibc/архитектуру загружаемых
mise-tools. Не переносить macOS-список приложений или системные сервисы механически.

## Proxmox: гипервизор

Хост — инфраструктурная система. Будущий минимальный профиль должен ограничиться
нужными административными клиентами и диагностикой. Никакого desktop, language
toolchain или локального Docker engine по умолчанию. Не менять repositories,
kernel, networking, storage, firewall, SSH daemon или cluster config пользовательским
dotfiles bootstrap. Их жизненный цикл относится к управлению Proxmox.

Проверить роли/права, обслуживание кластера, backup/recovery и отдельного non-root
оператора; нельзя предполагать, что аккаунт root — целевой пользователь dotfiles.
Официальная модель отдельно описывает VM и containers:
[Proxmox VE Administration Guide](https://pve.proxmox.com/pve-docs/pve-admin-guide.pdf).

## Proxmox Ubuntu VM и LXC

Guest-профиль — отдельный сценарий со своей поддерживаемой Ubuntu release,
архитектурой, package manager и user account. VM имеет собственное ядро, LXC
разделяет ядро хоста и имеет другие ограничения privileges/изоляции. Нельзя
считать их взаимозаменяемыми при установке Docker, FUSE или использовании systemd.

Cloud-init можно рассмотреть для создания гостя и пользователя, а common —
для его конфигурации после предоставления зависимостей. Desktop/terminal UX
по выбору, серверному гостю достаточно меньшего набора. Для LXC отдельно проверить
unprivileged mode, UID mapping, SSH, mounts, nesting и восстановление контейнера;
не включать nesting/privileged режим автоматически ради установки dev-tool.
